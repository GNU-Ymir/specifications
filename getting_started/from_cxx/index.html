    Step 1 · Foundations

    The toolchain and your first program

    Ymir is a compiled, statically typed systems language whose reference compiler, gyc, is a GCC frontend. You keep GCC's optimizer, its target support and its object format — what changes is the language in front of it.

    By the end of this step
    • Compile and run a Ymir program
    • Understand modules, and why there are no headers
    • Read the shape of a real project layout

    Hello, world

    Three departures from C++ are already visible. There is no header — a module is one file, and its public surface is whatever it marks pub. There is no preprocessor — use imports symbols from a module path, and the compiler reads the actual module rather than pasting text. And main takes no parameters unless you want them, in which case it takes a slice of strings: fn main (args : [[c8]]).

    println accepts a variadic list of values and, given a format string, substitutes % for each subsequent argument:

    Modules replace headers

    A file inside a package names its module on the first line. That line is how the compiler binds a file on disk to a name in the module tree, so it must agree with the file's path.

    The brace form std::{stream, conv} imports several siblings in one line. Submodules are declared with mod ::name;, and :: is the path separator throughout — for modules, for enum members, for static class members. It never means "pointer dereference", because Ymir has no -> member access.

    Because there is no textual inclusion, several C++ chores simply do not exist: no include guards, no forward declarations to break cycles, no distinction between a declaration and a definition that must be kept in sync, and no ODR violations from a header compiled with different flags in different translation units.

    Projects and building

    A project is described by gyllir.toml and built with gyllir build. The manifest names the compiler, the artefact type, the C libraries to link and the dependencies to fetch:

    gyllir build --release switches on optimization; gyllir test builds and runs the test binary. Tests are not a separate framework bolted on — a __test { ... } block is a language construct, so unit tests live beside the code they exercise and are compiled out of release builds.

    Orientation

    The single most useful corpus of example Ymir is the compiler's own test suite. Each case under test_resources/ is a complete, self-contained file paired with a golden file holding the exact diagnostic or semantic dump it produces. Every snippet in this tutorial is drawn from or modelled on those cases.

    Step 2 · Foundations

    Syntax essentials

    Everything in this step you can absorb by analogy with C++. It is worth reading closely anyway, because two small habits — expression-valued blocks and the -> operator — account for a large share of early confusion.

    Functions

    Blocks have values

    The last expression of a block, written without a trailing semicolon, is that block's value. a + b is therefore the return statement. Add a semicolon and it becomes a statement whose value is discarded, at which point the block's value is void and the function no longer type-checks.

    This applies to any block, not just function bodies, which makes if and match ordinary expressions and removes the need for the ternary operator:

    return still exists and is used for early exit. The idiom is: return when leaving early, bare final expression when producing the result.

    Named arguments use ->

    by-> 3 passes 3 to the parameter named by. This lets you supply a later default without positionally padding the ones before it, and it makes boolean arguments readable at the call site — shorten (s, max-> 10) rather than shorten(s, 10).

    Do not misread the arrow

    -> appears in exactly two places: introducing a return type (fn f ()-> i32) and naming an argument (f (by-> 3)). It is never member access. Ymir reaches members with . — even through a class reference — or with :. when the access mutates. You will meet that operator in Step 6.

    Bindings

    let introduces a binding; the type annotation is optional and inferred when omitted. Bindings are immutable by default — the inverse of C++, where you opt into const and most code never bothers.

    _ is the discard pattern; binding to it says "evaluate this and throw the result away" without provoking an unused-variable diagnostic. A leading underscore on a real name, as in _x_, is the convention for a binding that is deliberately unused.

    Control flow

    if, while, break and continue behave as you expect. for is always a range-based loop; there is no three-clause form, because a counting loop is expressed as a range.

    A range whose start exceeds its end counts down. That single rule replaces rbegin/rend, and it explains the pervasive for i in str.len .. 0us idiom in the compiler's own source — note that it yields len down to 1, which is why such loops index with i - 1us.

    match

    match is an expression, has no fallthrough, needs no break, and separates arms by juxtaposition rather than commas:

    This is a far more capable construct than switch — it destructures values, tests dynamic types, and binds parts of what it matched. Step 4 returns to it once there are aggregates to take apart.

    Operators

    Arithmetic, comparison and bitwise operators match C++. Two differences are worth memorising immediately:

    YmirMeaningC++ trap it removes
    ~, ~=Concatenation and append+ is arithmetic only, so "a" + 1 can never silently do pointer arithmetic
    ==Value equality, via opEqualsOn class references it compares contents, not addresses
    is, !isIdentity / type testDistinguishes "same object" from "equal value" explicitly

    Implicit numeric conversions are far more restricted than in C++: mixing widths or signedness generally requires an explicit cast!, and integer literals carry suffixes (1u32, 0us, 12u64) so their type is stated rather than deduced from context. The whole category of bugs around implicit integer promotion and narrowing largely disappears.

    Step 3 · Foundations

    Types and data structures

    Ymir builds into the language several things C++ delegates to the standard library — slices, maps, options, tuples. Because they are language types, they have literal syntax and the compiler reasons about them directly.

    Slices — one type for vector and span

    [T] is a slice: a pointer and a length. It covers what C++ splits between std::vector<T> (owning) and std::span<T> (viewing), with ownership handled by the garbage collector rather than by the type.

    Slicing is O(1) and shares storage, exactly like span. Unlike span, you cannot end up with one that outlives its buffer, because the buffer is reachable so long as the slice is. Indexing is bounds-checked, and an out-of-range index raises a catchable error rather than reading past the end.

    Static arrays with a compile-time length are written [T ; N], and [v ; N] is the repeat literal:

    Strings are slices of characters

    [c8] is a UTF-8 string, [c32] a UTF-32 one. A literal adopts the type required of it, and a suffix pins it explicitly:

    The encoding is part of the type, so it cannot be lost or confused the way std::string versus std::wstring versus "bytes that happen to be UTF-8" can be in C++.

    Tuples

    Multiple return values need no std::tie, no out-parameters and no ad-hoc struct. A one-element tuple is written with a trailing comma, (x,), to distinguish it from parenthesised grouping.

    Options

    (T)? is an optional T, and ? after a value builds one:

    Options are consumed by pattern matching rather than by an unchecked accessor, so there is no equivalent of dereferencing a disengaged std::optional. Note that an option wrapping a plain value involves no indirection — copying one is a stack copy and needs no alias, whereas an option wrapping a slice inherits the slice's borrowing rules.

    Maps

    [K => V] is an associative map with literal syntax:

    Lookup returns a (V)? rather than default-constructing an entry, so the classic C++ surprise where m[k] silently inserts does not arise — and nothing is thrown at the lookup itself. The absent case is simply a value you have to consume, by matching or by destructuring:

    A plain let only destructures patterns that cannot fail, which is why the fallible case goes through match or if let. The alias in the first match is the usual borrowing rule rather than anything specific to maps: binding the inner slice as dmut takes a mutable borrow, and Ymir never lets that happen implicitly. When you would rather assert than branch, .value is the terse form: a ["foo"].value throws when the option is empty. The throw belongs to the option, not to the map — reading it that way keeps the failure where it actually is.

    One constraint follows from the memory model: a map key must always be immutable. Mutating a key in place would invalidate the hash, so the type system forbids the situation instead of leaving it as undefined behaviour.

    Enumerations

    Ymir enums are closer to a named set of constants than to C++'s integer enum, and members may carry any type — including strings:

    Enum members are reached with ::, and an enum is a distinct type for overload resolution — given both fn foo (x : i32) and fn foo (x : X), passing X::A selects the second. This is the scoped-enum behaviour of enum class, without the unscoped variant existing at all.

    Aliases with def

    def names a type or a compile-time constant, covering both using/typedef and constexpr:

    Note the second line: because mutability is part of a type, an alias can carry it. That is genuinely useful and slightly dangerous — def MutList : dmut [i32] hides a dmut behind a name, so the reader of a declaration no longer sees it.

    List comprehensions

    This is the language-level replacement for std::transform with a back-inserter, and it composes with any iterable, including maps and user types that define iteration.

    Step 4 · Structuring data

    Three kinds of struct

    C++ has one aggregate and a set of conventions layered on top of it. Ymir turns the question "is this a value, a handle, or a unique owner?" into a keyword, and derives the memory behaviour from your answer.

    In C++, struct and class differ only in default access. Whether a type behaves as a value, a shared handle or a unique owner depends on which special members you write, whether you remembered to delete the others, and how disciplined your team is. The type system does not help you, and a type that is one thing today can silently become another when someone adds a member.

    recordValue type. Copied by value, no destructor.An aggregate structA (1, 2)
    entityOwned value. Has a destructor, is move-only.unique_ptr-style RAII typeA () + move
    classReference type. Heap allocated, GC'd, inheritable.shared_ptr<Base>copy A ()

    record — the default choice

    Fields are declared with let, constructors are named self, and field initialisation happens in a with clause — the equivalent of a member initializer list, and the only place fields may be initialised.

    No copy appears when constructing a record: it is a value, built in place. Notice that destructuring reuses the construction syntax, so a pattern reads like the call that produced it — and because arguments are named, neither is sensitive to field order.

    Records are generic in the same way functions are:

    class — the reference type

    A class is always a reference. The binding holds a handle; assignment shares the referent rather than duplicating it; the type is spelled &A when written out. Allocation uses copy, which is the same "produce a fresh object" operator you saw on slices.

    Reading that against C++:

    • over does double duty. class Dog over Animal is inheritance; pub over name is override. There is no virtual keyword — a public method is overridable unless the class is @final — and over is mandatory, so the C++ bug where a subtly different signature silently creates a new function instead of overriding cannot happen.
    • The receiver is an explicit parameter. fn name (self) is a const method; fn change (mut self) may mutate. There is no trailing const, and self. is required to touch a field, which removes the ambiguity about whether an identifier is a member, a local or a global.
    • Single inheritance only. Shared behaviour across unrelated hierarchies is expressed with traits, so there is no diamond problem and no virtual inheritance.
    • Operators are named methods — opEquals, opIndex, opIndexAssign, opDollar — rather than operator==. opDollar is what makes $ work inside your type's index expressions.
    • Classes are garbage collected. No delete, no ownership question to answer, no dangling handle. Deterministic release is what entity is for.

    Field methods

    @field marks a method callable without parentheses, so a computed property and a stored one are indistinguishable at the use site:

    trait — interfaces without a hierarchy

    A trait declares methods that an implementing type must provide, and may supply default bodies. It is adopted with impl. The important difference from a C++ abstract base class is that a record can implement a trait too:

    In C++, sharing an interface across types costs you a vtable and, in practice, heap allocation and reference semantics for everything that participates. Here the value type stays a value type. Common traits like Streamable, Hashable and Comparable!{T} are how the standard library hooks into printing, hashing and ordering — impl Streamable; with no body generates a sensible default, which is the equivalent of a derived operator<<.

    Now that there are aggregates, match shows its real range. It tests dynamic type, destructures fields by name, and binds parts of the match:

Patterns compose with the mutability system — ref mut and dmut inside a pattern mean exactly what they mean in a declaration, which is the subject of the next step.

    Step 5 · The memory model

    Mutability is a stack of levels

    This is the one part of Ymir with no C++ analogue to port. It is the source of most first-week compiler errors, and once it clicks, most of the rest of the language follows from it.

    By the end of this step
    • Read a type like mut [mut i32] level by level
    • Know precisely what dmut means and when mut is not enough
    • Diagnose "discard the constant property is prohibited" mechanically

    The problem with one qualifier

    C++ gives you const, applied at whatever position you write it: const int*, int* const, const int* const. In theory this is expressive. In practice most codebases reason about the outermost level and hope about the rest, which is why this compiles and does what it appears to forbid:

    The const stops at the first level. Everything reachable through it is unprotected, and nothing in the signature warns the caller. Ymir's answer is to track mutability at every indirection level independently and enforce the whole stack.

    Reading a type level by level

    Read from the outside in. Each level — the binding, then the slice it designates, then that slice's elements — carries its own mutability, and mut qualifies exactly one of them.

    A slice of integers, at three strengths
    [i32]
    bindingimmutable
    sliceimmutable
    elementsimmutable

    Read-only all the way down. Approximately const vector<const int>, except that C++ cannot really spell it.

    mut [i32]
    bindingmutable

    elementsimmutable

    You may repoint the binding at a different slice. You may not write through this one. a = other; is legal, a[0] = 1; is not.

    mut [mut i32]
    bindingmutable
    slicemutable
    elementsmutable

    Fully writable. dmut is the shorthand that produces exactly this.

    dmut — deeply mutable — means mutable at every level, however deep the type goes. For [[i32]] it covers three levels of indirection; you would otherwise write mut [mut [mut i32]]. This is why let dmut a = copy [1, 2, 3]; is the overwhelmingly common declaration form, and why mut alone on anything with indirection is nearly always a mistake.

    The most common early error

    mut is not an abbreviation of dmut. On a slice, mut makes only the binding assignable and leaves the data immutable. If the compiler rejects a write you believe should be allowed, check which of the two you wrote before questioning anything else.

    The one rule: mutability may be lost, never gained

    A value may always be used where less mutability is required. It may never be used where more is required. C++ agrees in principle, then permits const_cast, pointer decay and template deduction to launder it away. Ymir refuses at every level, and provides no cast to override the decision.

    Here both branches of an if must produce one type. They differ, so the result can only be the weaker of the two — and the weaker one does not fit dmut b:

    Error : when validating test17::main --> test_resources/control_flow/test17.yr:(1,4) 1 ┃ fn main () { ╋ ^^^^ ┃ Error : discard the constant property is prohibited ┃ --> test_resources/control_flow/test17.yr:(4,14) ┃ 4 ┃ let dmut b = if cond { ┃ ╋ ^ ┃ ┃ Note : from mut [i32] to mut [mut i32] ┃ ┗━━━━━━━ ┗━━━━━┻━

    How to read this diagnostic

    The Error line is the same for every mutability failure. It tells you the category, not the cause. The information is in the Note:

    from mut [i32] to mut [mut i32] — the compiler has a value of the first type and a context demanding the second. Compare them position by position: the outer mut matches; the inner one is present in the requirement and absent in the value. That is the level at fault. The fix is always one of two things: strengthen the source (make a a dmut), or weaken the destination (drop b to mut).

    Getting into the habit of reading only that line will convert most of these errors from mysterious to mechanical.

    Where the levels come from

    Mutability is inferred from how a value was produced, and it is worth knowing which producers give you what:

    ExpressionResulting typeWhy
    [1, 2, 3][i32]A constant literal — nothing is allocated, nothing is writable
    copy [1, 2, 3]mut [mut i32]Fresh allocation, so the compiler knows nobody else holds it
    let a = copy [...]mut [i32]The binding was not declared dmut, so the inner level is dropped on the way in
    let dmut a = copy [...]mut [mut i32]Full mutability is requested and available

    Row three is the subtle one and explains the rejected example above: let a = copy [1, 2, 3]; does not give you a deeply mutable slice, even though copy produced one, because the binding did not ask for it — and once the mutability has been dropped, it can never be recovered.

    Mutability on fields and parameters

    The same annotations appear on record and class fields, where they describe what a holder of the aggregate may modify:

    Two rules constrain parameters, and both exist to catch meaningless declarations. A parameter cannot be mutable unless it is a reference or borrows mutable data — mutating your own private copy of an i32 is invisible to the caller, so it is far more often a misunderstanding than an intent. The same rule applies to loop iterators.

    With the level system in hand, the next step covers the operators that let values move between levels: alias, copy, dcopy and ref.

    Step 6 · The memory model

    Aliasing, copying and references

    If Step 5 was the type system, this is the vocabulary. Four operators cover every way two names can relate to the same memory — and Ymir requires you to name which one you meant.

    OperatorEffectC++ analogue
    alias vNothing copied; a mutable borrow is createdTaking a T& to the pointee
    copy vOne level. Fresh outer container, shared contentsCopying a vector<shared_ptr<T>>
    dcopy vEvery level, recursivelyA hand-written deep clone
    ref vA reference to the binding itselfT& parameter

    alias — borrowing, out loud

    When two names can reach the same mutable memory, Ymir requires you to say so at the point where the sharing begins. alias generates no code; it is a claim about intent that the compiler verifies.

    Now compare a function call. Given C++'s void fill (std::vector<int>& v), the call fill (v) is indistinguishable from a by-value call at the call site; you must open the header to learn that v can change. In Ymir the mutation is visible where it happens:

    The compiler enforces this by rejecting any implicit alias — a place where mutable memory would become shared without the operator appearing:

    Error : discard the constant property is prohibited --> test_resources/control_flow/test10.yr:(3,15) 3 ┃ let (dmut a : [i32], _ : [i32]) = t; ╋ ^ ┃ Note : implicit alias of type mut [mut i32] is prohibited, ┃ it implicitly gives up on borrowings of mutable values ┗━━━━━┻━

    Symmetrically, Ymir rejects alias where it would be pointless: aliasing to create a merely constant borrowing, or aliasing something already implicitly aliased, are both errors rather than harmless noise. The consequence is that every alias surviving in real code marks a genuine mutable sharing point — which makes it a high-signal thing to grep for during review, in a way that & in C++ never is.

    Which types need it

    Only aliasable types — those with indirection the compiler must track: slices, maps, class references, and aggregates containing them. Copying an i32, an f64 or an option wrapping one is a plain stack copy and needs no operator. This is why let dmut b = a; above is legal without alias when the value is not aliasable, and an error when it is.

    copy and dcopy — choosing a depth

    C++ copy constructors are implicit and recursive, which is where a great deal of accidental cost lives — the classic profiling discovery that a vector<string> is being deep-copied on every call. Ymir has no implicit copy of indirect data. You request it, and you state the depth.

    copy has a precise definition: it is one-level, and it applies to slices, static arrays, maps, and class constructor calls. Everything else has no one-level copy and the compiler says so plainly — no copy exists for type …. That is a feature: it means a type that cannot be sensibly shallow-copied will not be shallow-copied by accident.

    Seen this way, copy is a single consistent idea — produce a fresh outer object — which explains why the same keyword allocates a class (copy A ()) and a slice (copy [1, 2, 3]). An array literal without it is a constant, and forgetting it is common enough that the compiler asks directly whether you meant to enclose the expression in a copy.

    ref — a genuine reference to the binding

    alias shares the memory a value points at. To let a callee reassign the caller's binding itself — a true T& — use ref, at both the declaration and the call:

    Declaring a as mut here fails, with the familiar note — from mut [i32] to mut [mut i32]. The rule of Step 5 applied at a parameter boundary. Requiring ref at the call site as well means that, as with alias, you never have to consult a signature to know whether your variable can be rebound underneath you.

    The :. operator

    The same philosophy reaches method calls. Invoking a method declared mut self requires :. rather than .:

    In C++, obj.foo() tells you nothing about whether obj changes. In Ymir the punctuation tells you, at every call, with no lookup required. The operator is unified across everything that can be mutated through a handle — class fields and methods, record and entity fields, map fields and methods — and its sibling :[ does the same job for mutating index access:

    The through-line

    alias, ref, :. and :[ are four spellings of one design decision: anything that lets a value change under a name must be visible at the place it happens, not only in a declaration somewhere else. That is the property C++ gives up when it allows f(v) to mutate v, and it is what makes Ymir code auditable by reading the call site.

    Step 7 · The memory model

    Ownership, destruction and lifetime

    C++ answers memory safety with one mechanism — deterministic destruction — and asks you to express everything through it. Ymir splits the problem: the collector handles memory, entities handle resources, and scope guards handle everything else.

    Memory: garbage collected

    Class instances and slices are managed by a garbage collector. There is no delete, no ownership question to answer for plain data, and no dangling reference. A slice into a buffer keeps the buffer alive, so the C++ hazard of a span or iterator outliving its container does not exist.

    This is a real trade — you accept a collector to remove a category of bug — and it is why Ymir needs a second mechanism for resources where when matters.

    Resources: the entity

    An entity is a value type that owns something and must release it at a predictable moment. It is the only aggregate permitted to declare a destructor, __dtor, and it is move-only.

    Entities compose. An entity holding another entity destroys its member as part of its own destruction, so a tree of resources unwinds in order without any of it being written out:

    move — a transfer the compiler tracks

    Handing an entity somewhere else requires move, which transfers ownership and resets the source:

    The distinction from std::move is worth dwelling on, because the names are misleadingly similar:

    C++ std::moveYmir move
    What it isA cast to rvalue referenceAn ownership transfer
    Does it move?No — it enables an overload that mightYes
    Source afterwardsValid but unspecified; still destructibleReset; using it is a compile error
    Use after moveCompiles, often a bugRejected

    Because entities cannot be copied at all, there is no copy constructor to remember to delete, no moved-from-but-still-destructible state to reason about, and no risk of reading a hollowed-out object. Moving out of a field works the same way, which is how ownership escapes a containing structure:

    Scope guards: cleanup not attached to an object

    Plenty of cleanup does not belong to a type — restoring a flag, logging a duration, releasing a lock taken by a C API. In C++ that means either a bespoke RAII wrapper or the goto cleanup pattern. Ymir has scope guards:

    These are the language-level version of scope_exit, plus the two variants C++ does not have in the standard. failure in particular expresses "undo this if something went wrong" without a boolean flag and a destructor that inspects uncaught_exceptions.

    Choosing a mechanism

    Use a class for shared graph-shaped data — the collector removes the ownership question entirely. Use an entity when release must happen at a known point: file descriptors, sockets, locks, GPU handles. Use a scope guard when the cleanup belongs to a block rather than to a value. Reach for a record for everything else, which is most things.

    What this buys you

    The three C++ bug classes this structure removes, stated plainly: no use-after-free, because collected memory stays alive while reachable and entity memory cannot be used after a move; no double-free, because entities are move-only and destroyed exactly once; and no leak from a forgotten branch, because destruction and scope guards are attached to scopes rather than to your remembering to call something.

    Step 8 · Beyond the basics

    Functions in depth

    Lambdas, delegates, deferred arguments and argument expansion. Several of these have C++ equivalents that are considerably more ceremonious.

    Lambdas and closures

    A lambda is written with pipes around its parameters and => before its body. Parameter types are inferred:

    The memory rules apply inside the parameter list exactly as they do elsewhere, so a lambda that mutates its argument declares that intent and its caller states it too:

    Note what is absent: a capture list. C++ makes you choose between [=] and [&], and choosing [&] on a lambda that outlives the frame is a well-known way to produce a dangling reference. In Ymir, captured values are reachable and therefore kept alive by the collector, and captured mutable data obeys the same aliasing rules as everywhere else. There is a copy form for a closure when you want its captures duplicated, and the compiler will tell you if the closure captures nothing and the copy is pointless.

    Error messages

    The practical difference from C++ shows up when instantiation fails. Rather than a wall of substitution attempts, the compiler reports the failure once per candidate, names the binding it inferred, and points at the argument responsible:

    Error : the call operator is not defined for test5::X::foo {T}(a: T, b: A!{T}) and {'u'c8: c8, _: A!{i32}} --> test_resources/struct/test5.yr:(22,12) 22 ┃ X::foo ('u', X::bar ()); ╋ ^ ┃ Note : candidate test5::X::foo {T}(a: T, b: A!{T}) ┃ ┃ Error : incompatible types A!{c8} and A!{i32} ┃ ┃ ╋ note: for parameter b: A!{c8} ┃ ┃ Note : with {T=> c8} ┃ ┗━━━━━━ ┗━━━━━┻━

    The final line — with {T=> c8} — is what you usually want: it tells you what T was deduced as, which is nearly always where the misunderstanding is.

    Macros

    Beyond generics, Ymir has real macros: not text substitution, but grammar rules the compiler parses. A macro declares a syntax it accepts and the code it expands to:

    Because a macro defines a grammar, it can accept syntax that is not otherwise valid Ymir — embedding an entire JSON literal, say, parsed and checked at compile time. That is a different tool from the C preprocessor in every respect: it is hygienic, it is typed, and it cannot silently redefine an identifier in a file that includes it.

    Step 10 · Beyond the basics

    Errors and exceptions

    Ymir has exceptions, and unlike C++ they are checked. What can be thrown is part of a function's signature, and callers must do something about it.

    throws is part of the signature

    Three things differ from C++. The exception specification is enforced, not documentation — calling risky without handling or propagating will not compile, where C++ compiles it and calls std::terminate at runtime. Handlers are patterns, using the same matching machinery as match. And a try block is an expression, so each arm produces the value of the whole construct rather than assigning into a variable declared beforehand.

    A function that propagates rather than handles simply declares the exception itself, which makes the error paths through a program readable from signatures alone — the thing noexcept gestures at but cannot deliver, since C++ abandoned checked specifications for good reasons that Ymir's design avoids.

    Common errors

    Several ordinary operations can fail and therefore throw: an out-of-bounds index, reading .value on an empty option, a failed assert. This is why throws AssertError appears on so many test functions:

    panic aborts unconditionally; it is the deliberate "this cannot happen" terminator, and being a keyword it is greppable in a way that a call to std::abort is not. The catch-all pattern is _.

    Scope guards and exceptions

    The guards introduced in Step 7 are how cleanup interacts with unwinding:

    There is one rule with genuine subtlety, worth stating because it is easy to trip over: a throw inside a scope-guard body is illegal only if it can actually escape that body uncaught. A throw nested inside a block that catches everything it can raise does not count as crossing the guard, even though it sits lexically within one. The reasoning is the same as C++'s prohibition on throwing from a destructor during unwinding — but Ymir checks it precisely rather than making the whole category undefined.

    Step 11 · Systems work

    Layout, alignment and C interop

    When you care about the bytes rather than the types: controlling field placement, querying sizes, and talking to code that was not written in Ymir.

    Default layout

    By default the compiler places a record's fields with natural alignment, as a C++ compiler would, and you should not depend on the order. When the layout itself is the point — a wire format, a hardware register, a tagged union — two attributes take control.

    @overlaid — a union

    All fields share an offset. The type's size is that of its largest member, and only one field is meaningfully live at a time:

    Ymir enforces a rule C++ leaves to you: an overlaid type may not contain aliasable types, with pointers as the deliberate exception. A union of two slices would let you fabricate a slice from unrelated bytes and walk straight past everything Steps 5 and 6 established, so it is rejected outright rather than left as undefined behaviour:

    Error : type mut [mut i32] cannot be embedded within an union type ┃ Note : union cannot contain aliasable types, ┃ with the exceptions of pointer types ┗━━━━━┻━

    @packed — no padding

    @packed removes inter-field padding, matching #pragma pack(1) or __attribute__((packed)). The trade is the same as in C++: density in exchange for alignment, and unaligned access costs on platforms that care about it.

    Querying sizes

    ::size is the sizeof equivalent and is available at compile time, so layout invariants can be asserted in the compiler rather than discovered in a test.

    Talking to C

    extern (C) declares a symbol with C linkage — functions and globals alike:

    Libraries to link are named in gyllir.toml — the libraries = ["gmp", "mpfr"] line from Step 1 is exactly this. Since the backend is GCC, the object format, calling conventions and debug information all match what your existing C and C++ toolchain produces.

    unsafe

    Raw pointer work is available and must be named as such. An unsafe region suspends the ordinary guarantees, which makes the places where the compiler is no longer checking for you an explicit, searchable set — the same reasoning as alias, applied one level down.

    A practical note on FFI

    Crossing into C means leaving the collector's knowledge. A pointer handed to a C library that stores it beyond the call is not, by itself, keeping anything alive. The usual discipline applies: keep a Ymir-side reference for as long as the foreign side holds the pointer, and prefer an entity to own the handle so release happens exactly once at a known point.

    Seven reliable mistakes

    1. A stray semicolon changes the return type. { a + b } returns the sum; { a + b; } returns void. When the compiler complains about a mismatch against void, look for the semicolon before you question the signature.
    2. mut is not dmut. On anything with indirection, mut makes the binding assignable and leaves the data immutable. Most "why can't I write to this" errors are this and nothing else.
    3. Read the Note line, not the Error line. "discard the constant property is prohibited" is the same text for every mutability failure. The from … to … note beneath it identifies the level at fault.
    4. Forgetting copy. let dmut a = [1, 2, 3]; does not allocate — that is a constant. The compiler asks, literally, whether you meant to enclose it in a copy.
    5. -> is not member access. It introduces a return type and names an argument. Members are always reached with . or :., even through a class reference.
    6. Only entities have destructors. __dtor in a record is an error. Needing deterministic cleanup means you picked the wrong aggregate.
    7. Exceptions are checked. Calling a throws function without handling or propagating will not compile — pleasantly unlike C++, where it compiles and terminates at runtime.

    Where to go next

    The language specification and the reference book cover concurrency, macros and the standard library far past what a twelve-step introduction can. For experimenting, the compiler's own test suite remains the best corpus: every case under test_resources/ is a complete file paired with the exact diagnostic or semantic dump it produces, which makes it the fastest way to find out what the compiler really does with a construct.

    The most productive next exercise is to port something small you already own — a parser, a data structure, a CLI tool. The syntax will take an afternoon. The mutability levels will take a week, and they are the part worth the week.
